# 投入记录与估算口径

用户2026-10-30允许按公开资料作粗略估算。以下明确区分记录、估算、未来计划；不会将行业研究中的加速比例换算成作者实际工时。

## 有记录的会话墙钟

来自各阶段state的executionStartedAt/CompletedAt（UTC+08:00），准备时仅作JSON日期运算：

| 阶段 | 起止 | 分钟 |
| --- | --- | --- |
| P0 | 2026-10-29 17:17:02～18:07:26 | 50.40 |
| P1 | 2026-10-29 22:52:38～2026-10-30 01:52:15 | 179.62 |
| P1.1 | 2026-10-30 11:18:40～12:36:25 | 77.75 |
| P1.2 | 2026-10-30 12:44:33～15:57:22 | 192.82 |
| 合计 | 四个已记录执行区间 | 500.59，约8.34小时 |

包含构建、CI等待、验证和修正；不是纯编码时间或人类工时。不包含未完整计时的各轮准备、阶段间隔、15:57后的两处修正和P2；不将三个并行worker相加。P2执行另记录其真实区间，最后总结不能把当前值当全项目精确总投入。

## 人工投入粗估

在没有本人计时表的情况下，给用户的暂定区间为**约2～4小时，低置信度活动估算，并非实测或作者确认**：需求阅读/方向核对0.5～1小时，分阶段交互和设计反馈0.5～1小时，界面/流程试用0.75～1.5小时，收尾材料核对0.25～0.5小时。此分解是按已知活动类型设置的假设预算，不证明实际花了这些时间，也不包含未来P2尚未发生的人工审阅。

最终README建议直说：“人工投入未独立计时，按需求阅读、指导与试用等活动粗估约2～4小时；开发/验证会话的已记录执行区间另列。估算非实测，未累加并行AI时间。”P2只汇总实际完成活动，未来计划不提前计入实际；若作者后来给出实际数字，以作者记录替代此区间。

## 网上资料能提供什么

[Microsoft Research的SPACE研究](https://www.microsoft.com/en-us/research/publication/the-space-of-developer-productivity-theres-more-to-it-than-you-think/)说明开发生产率不能由单一指标代表。[GitHub受控实验](https://github.blog/news-insights/research/research-quantifying-github-copilots-impact-on-developer-productivity-and-happiness/)是特定JavaScript HTTP server任务的对照结果，不能推算这份Next/Java/MySQL项目或作者阅读/试用时间。公开资料仅用于选择记录维度；**没有找到与本项目同范围、同人同工具可直接换算的工时数据**。2～4小时来自上面的项目活动假设，不归因于网上实测数据。

P2计划5～8小时工作窗口是执行前预算；P2最终报告必须改写为实际检查、整理、等待和修正的记录/未知，不能沿用预算冒称实际投入。
